# Contributing to AI Future Lab | المساهمة في AI Future Lab

**English | [العربية](#الدليل-بالعربية)**

Thank you for your interest in AI Future Lab.

AI Future Lab is currently a concept, system-architecture, research, and future-product project. The complete AI urban-planning platform has not yet been implemented. Contributions should help improve the clarity, safety, technical direction, research quality, or future implementation of the idea.

This repository does not currently grant a general open-source license. Public visibility does not automatically give permission to copy, republish, sell, commercially use, or present the project as another person’s original work. See [LICENSE.md](LICENSE.md) and use the permission-request process when needed.

## 3. Contribution Types

### A. Feedback Issue

Use this when you want to explain:

- A weakness in the concept
- A missing workflow
- A technical risk
- A confusing explanation
- A suggested improvement

A useful feedback issue includes:

```text
Area:
Problem:
Why it matters:
Suggested change:
Evidence or professional experience:
Expected benefit:
```

### B. Documentation Correction

Use this for:

- Spelling
- Grammar
- Broken link
- Incorrect file reference
- Unclear wording
- Arabic translation correction

Please explain whether the change affects meaning or only presentation.

### C. Architecture Proposal

A strong architecture proposal includes:

- Current problem
- Proposed component
- Inputs
- Outputs
- Dependencies
- Failure cases
- Security concerns
- Human approval requirement
- Implementation difficulty

### D. Workflow Proposal

A workflow proposal should explain:

1. Trigger
2. Input
3. Processing steps
4. Decisions
5. Output
6. Errors
7. Recovery
8. Reviewer or approver

### E. Code Contribution

Future code contributions should include:

- Clear purpose
- Setup instructions
- Comments
- Error handling
- Input validation
- Tests where possible
- Security notes
- Honest limitations

Do not submit code that claims professional planning accuracy without evidence and validation.

### F. Permission Request

Use this when requesting permission to:

- Reuse documentation
- Reuse diagrams
- Present the project in another publication
- Use part of the concept commercially
- Build a derivative version
- Include the project in an event, article, video, or research activity

A request should state:

- Name or organization
- Purpose
- Material requested
- Public or private use
- Educational, research, nonprofit, or commercial use
- Planned attribution
- Expected audience
- Requested period
- Contact method that does not expose unnecessary personal information

Submitting a request does not mean permission has been granted. Written approval is required.

### G. Collaboration Request

A collaboration request should explain:

- Who you are or which organization you represent
- Area of expertise
- Collaboration idea
- Expected role of the project creator
- Expected contribution from your side
- Timeline
- Public or confidential nature
- Ownership expectations
- Whether funding or commercial use is involved

---

## 4. Before Opening an Issue

Please:

1. Read the main README.
2. Read the relevant documentation.
3. Check whether a similar issue already exists.
4. Remove private or confidential information.
5. Use a clear title.
6. Separate facts from opinions.
7. State when information is uncertain.

---

## 5. Writing a Good Issue

Good title:

```text
Improve explanation of digital-twin versioning
```

Weak title:

```text
Project problem
```

A good issue is:

- Respectful
- Specific
- Understandable
- Connected to a project file or workflow
- Honest about uncertainty
- Focused on one main subject

---

## 6. Pull Request Process

When submitting a pull request:

1. Explain the problem.
2. Explain the change.
3. List affected files.
4. State whether English and Arabic are both updated.
5. Explain any technical assumptions.
6. Include tests for code changes where possible.
7. Confirm that no secrets or private data are included.
8. Confirm that you have the right to submit the content.
9. Wait for review.
10. Make requested corrections.

A pull request may be rejected when it:

- Copies copyrighted work without permission
- Exposes private data
- Adds unsafe code
- Makes unsupported claims
- Changes the project’s ownership or purpose
- Removes important limitations
- Adds unrelated advertising
- Is disrespectful or harmful

---

## 7. Documentation Style

Documentation should be:

- Clear
- Professional
- Honest
- Detailed enough for a new reader
- Understandable to non-specialists
- Consistent in terminology

Use these status words carefully:

- **Current:** exists now
- **Starter:** early code exists but is not fully tested
- **Planned:** intended for a future phase
- **Proposed:** architecture or design idea
- **Advanced future:** requires major future work
- **Approved:** reviewed by an authorized human inside a project workflow

Do not use “completed,” “production-ready,” “government-approved,” or “professionally validated” unless evidence exists.

---

## 8. Arabic and English Contributions

The project aims to support Arabic and English readers.

When updating translated files:

- Preserve numbers.
- Preserve status labels.
- Preserve warnings.
- Preserve technical meaning.
- Avoid translating product or technical terms in a misleading way.
- Link the Arabic and English versions.

A language improvement should not secretly change the project concept.

---

## 9. Code Quality Expectations

Future code should:

- Use meaningful names
- Include comments for difficult logic
- Validate user input
- Handle errors
- Avoid hardcoded secrets
- Use configuration files or environment variables
- Record dependencies
- Include setup instructions
- Explain expected output
- Explain limitations
- Avoid unnecessary complexity

---

## 10. AI Contribution Rules

AI-assisted contributions are allowed only when the contributor reviews and takes responsibility for the result.

Do not submit:

- Unreviewed generated code
- Invented references
- Fake test results
- Fake performance numbers
- Fake screenshots
- Claims that a model was tested when it was not
- AI output containing private data

Clearly state when a proposal is conceptual or untested.

---

## 11. Security and Privacy

Never submit:

- Passwords
- API keys
- Tokens
- Personal identification
- Phone numbers
- Home addresses
- Private school information
- Confidential government data
- Confidential company data
- Restricted infrastructure data

Sensitive security reports should follow [SECURITY.md](SECURITY.md), not a public detailed issue.

---

## 12. Ownership, Attribution, and Permission

By contributing, you confirm that:

- You created the submitted content or have permission to submit it.
- Your contribution does not intentionally violate another person’s rights.
- You understand that project maintainers may edit, reject, or remove it.
- The contribution does not transfer ownership of the complete AI Future Lab concept to you.

Because the repository is currently All Rights Reserved, acceptance of a contribution does not automatically create a broad public license for the whole project.

Specific ownership and licensing terms may need to be agreed before major code, commercial, research, or institutional collaboration.

---

## 13. Review Process

A contribution may be reviewed for:

- Relevance
- Accuracy
- Safety
- Privacy
- Clarity
- Technical quality
- Project direction
- Language consistency
- Copyright and permission
- Maintenance burden

Possible outcomes:

- Accepted
- Accepted with edits
- More information requested
- Deferred to a later roadmap phase
- Declined

A declined contribution is not necessarily a statement that the idea is bad. It may be outside the current scope.

---

## 14. Respectful Community Standard

Participants should:

- Discuss ideas, not attack people.
- Explain disagreements calmly.
- Welcome beginner questions.
- Avoid discrimination or harassment.
- Avoid pressure to share private information.
- Respect the project creator’s age and privacy.
- Avoid contacting the creator through unauthorized personal channels.

---

## 15. Current Contribution Priorities

Most useful now:

1. Review documentation clarity.
2. Review urban-planning assumptions.
3. Review AI architecture.
4. Review safety and governance.
5. Improve Arabic and English explanations.
6. Suggest a structured City Brief schema.
7. Suggest safe first-prototype tests.
8. Review exported workflow images when added.

Not a current priority:

- Building a complete Unreal project
- Production government integrations
- Real-time infrastructure control

- Large autonomous-agent systems

# الدليل بالعربية

## 1. كيف تساهم؟

يمكن المساهمة من خلال:

- ملاحظات بناءة
- مراجعة هندسة النظام
- ملاحظات تخطيط حضري
- ملاحظات ذكاء اصطناعي
- ملاحظات GIS والتوأم الرقمي
- مراجعة السلامة والحوكمة
- تصحيح التوثيق
- تحسين اللغة العربية أو الإنجليزية
- اقتراح مسارات عمل
- اقتراح أكواد مستقبلية
- طلب تعاون
- طلب إذن

---

## 2. الملاحظات المفيدة

الملاحظة الجيدة تشرح:

```text
المجال:
المشكلة:
لماذا هي مهمة:
التغيير المقترح:
الدليل أو الخبرة:
الفائدة المتوقعة:
```

لا تكتب فقط: «المشروع غير صحيح» أو «طوروه أكثر» بدون شرح.

---

## 3. طلب الإذن

استخدم طلب الإذن عندما تريد:

- استخدام جزء من التوثيق
- استخدام الرسومات
- عرض المشروع في منشور أو فيديو
- استخدام الفكرة تجاريًا
- إنشاء نسخة مشتقة
- إدخال المشروع في فعالية أو بحث

يجب أن يتضمن الطلب:

- اسم الشخص أو الجهة
- الغرض
- الجزء المطلوب
- نوع الاستخدام
- هل هو تعليمي أو بحثي أو تجاري؟
- طريقة ذكر المصدر وصاحب المشروع
- الجمهور المتوقع
- مدة الاستخدام

إرسال الطلب لا يعني الموافقة. يجب الحصول على موافقة مكتوبة.

---

## 4. طلب التعاون

اشرح:

- من أنت أو ما الجهة التي تمثلها؟
- ما خبرتك؟
- ما فكرة التعاون؟
- ماذا تتوقع من صاحب المشروع؟
- ماذا ستقدم أنت؟
- ما المدة؟
- هل المشروع علني أم سري؟
- هل يوجد استخدام تجاري أو تمويل؟
- ما توقعات الملكية؟

---

## 5. قبل فتح Issue

1. اقرأ الصفحة الرئيسية.
2. اقرأ الملف المتعلق بموضوعك.
3. تأكد أن السؤال غير مكرر.
4. احذف المعلومات الخاصة.
5. اكتب عنوانًا واضحًا.
6. افصل الحقيقة عن الرأي.
7. وضّح الأشياء غير المؤكدة.

---

## 6. تعديل التوثيق

يجب أن يكون التوثيق:

- واضحًا
- صادقًا
- منظمًا
- مفهومًا لغير المتخصص
- ثابتًا في المصطلحات

استخدم كلمات الحالة بدقة:

- حالي
- نموذج أولي
- مخطط
- مقترح
- مستقبلي
- معتمد

لا تقل إن النظام مكتمل أو معتمد رسميًا بلا دليل.

---

## 7. المساهمات البرمجية

يجب أن تحتوي على:

- هدف واضح
- خطوات تشغيل
- شرح للكود
- التحقق من المدخلات
- معالجة الأخطاء
- اختبارات إن أمكن
- ملاحظات أمان
- حدود واضحة

لا تضع مفاتيح API أو كلمات مرور داخل الكود.

---

## 8. استخدام الذكاء الاصطناعي في المساهمة

يسمح بالمساعدة من الذكاء الاصطناعي، لكن الشخص الذي يرسل المساهمة مسؤول عن مراجعتها.

ممنوع إرسال:

- كود مولد بلا مراجعة
- مصادر مختلقة
- نتائج اختبار مزيفة
- أرقام أداء غير حقيقية
- صور مزيفة على أنها منصة تعمل
- معلومات خاصة

---

## 9. الخصوصية

لا تنشر:

- كلمات مرور
- مفاتيح API
- رقم الهاتف
- عنوان المنزل
- معلومات المدرسة
- وثائق الهوية
- بيانات حكومية أو شركات سرية

مشكلات الأمان الحساسة تتبع ملف [SECURITY.md](SECURITY.md).

---

## 10. الملكية

المستودع حاليًا لا يمنح ترخيصًا مفتوحًا عامًا.

مشاهدة المشروع لا تعني السماح بنسخه أو بيعه أو نسبه لشخص آخر.

المساهم يؤكد أنه يملك حق إرسال المحتوى، وقبول مساهمته لا ينقل له ملكية المشروع كاملًا.

التعاون الكبير أو التجاري قد يحتاج اتفاقًا واضحًا حول الملكية والإذن والترخيص.

---

## 11. الأولويات الحالية

الأكثر فائدة الآن:

1. مراجعة وضوح الشرح.
2. مراجعة فكرة التخطيط الحضري.
3. مراجعة هندسة الذكاء الاصطناعي.
4. مراجعة الأمان والحوكمة.
5. تحسين العربية والإنجليزية.
6. اقتراح City Brief منظم.
7. اقتراح اختبارات للنموذج الأول.

المحركات ثلاثية الأبعاد والتكاملات الاحترافية ليست الأولوية الحالية.
